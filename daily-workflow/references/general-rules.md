# 通用规则

## 模块专项规范

### 目录结构

模块专项规范存放在 `references/modules/` 目录下，每个模块一个 md 文件。新建模块规范时复制 `_template.md` 并按需填写。

### 加载机制

- **自动匹配**：第一步需求分析时，根据 PRD 内容和涉及的代码目录，对比各模块 md 中的"适用范围"字段自动匹配
- **手动指定**：用户在启动时说"开启 dw + PRD链接，模块：xxx"
- 匹配结果记录到管理文件中，后续步骤自动引用，不重复询问

### 叠加规则

模块专项规范中的各章节会叠加到对应的通用规范上，不会覆盖通用规范：

| 模块规范章节 | 叠加到 | 生效步骤 |
|-------------|--------|----------|
| 额外编码约束 | coding-standards.md | 第三步：代码开发 |
| 额外 CR 检查项 | cr-general 检查维度 | 第五步：AI CR |
| 额外测试场景 | unit-testing.md 单元测试 | 第六步：单元测试 |
| 特殊接口约定 | 接口联调参考 | 第四步：接口联调 |

### 新增模块规范

用户可以随时说"新增模块规范：xxx"，AI 会基于 `_template.md` 创建新的模块规范文件，并询问用户填写各章节内容。

## 强制执行清单（Hard Rules）

> **AI 必须在每个步骤进入时，按顺序逐条执行以下动作，不可跳过、不可延后、不可只在对话中输出而不执行写入。**
> 违反任何一条都视为执行失败，必须立即补做。

### 进入第一步（需求分析）时

1. ✅ 读取 PRD 内容（飞书 `fetch-doc` 或本地文件）
2. ✅ 创建 Git 分支（开发模式）
3. ✅ 创建 `dw-state.json` 条目（状态"分析中"）
4. ✅ 在 `dw-daily.md` Doing 区插入新需求条目
5. ✅ 执行需求分析（代码对照 + 10 维度检查）
6. ✅ 将需求分析文档写入 `dw-docs/{需求名}/requirements.md`
7. ✅ 如有矛盾/歧义，在文档末尾写出"待确认项"章节，等待用户作答
8. ✅ 更新 `dw-state.json` 的 `documents.requirement_analysis` 和 `context`
9. ✅ 在对话中展示分析报告摘要，询问用户决策

### 进入第二步（设计文档）时

1. ✅ 读取 `dw-state.json` 中的 context（获取前序信息）
2. ✅ 生成设计文档
3. ✅ 将设计文档写入 `dw-docs/{需求名}/dev-design.md`
4. ✅ 如有多种方案需要决策，在文档末尾写出"待确认项"章节，等待用户作答
5. ✅ 更新 `dw-state.json` 的 `documents.design`、`context.design_decisions`、`context.tech_highlights`
6. ✅ 更新 `dw-daily.md` 追加当日记录
7. ✅ 在对话中展示设计文档摘要，询问用户确认
8. ✅ 用户确认后，询问"是否需要同步输出一份飞书文档？"

### 进入第三步（代码开发）时

1. ✅ 读取 `dw-state.json` 中的 context
2. ✅ 确认 Git 分支正确
3. ✅ 询问接口文档（如未提供）
4. ✅ 基于设计文档生成代码
5. ✅ ESLint 检查通过
6. ✅ 更新 `dw-daily.md` 追加当日记录
7. ✅ 更新 `dw-state.json` 状态

### 进入第五步（AI CR）时

1. ✅ 读取 `dw-state.json` 中的 context.affected_modules 确定走查范围
2. ✅ 执行 CR
3. ✅ 代码规范类问题自动修复
4. ✅ 将走查报告写入 `dw-docs/{需求名}/cr-report.md`
5. ✅ 更新 `dw-daily.md` 追加当日记录
6. ✅ 更新 `dw-state.json`

### 进入第六步（单元测试）时

1. ✅ 生成单元测试
2. ✅ 运行测试
3. ✅ 将测试报告写入 `dw-docs/{需求名}/unit-test-report.md`
4. ✅ 更新 `dw-daily.md` 追加当日记录
5. ✅ 更新 `dw-state.json`

### 进入第七步（提测）时

1. ✅ 生成提测文档写入 `dw-docs/{需求名}/test-submit.md`
2. ✅ 更新 `dw-daily.md` 追加当日记录
3. ✅ 更新 `dw-state.json` 状态为"已提测"
4. ✅ 用户确认后，询问"是否需要同步输出一份飞书文档？"

### 通用规则

- 每个步骤完成时，**必须同时**更新 `dw-daily.md` 和 `dw-state.json`，不能只做其中一个
- 对话中的输出是给用户看的摘要，**不能替代**实际的文件写入动作

## 飞书同步规则

飞书文档是**可选同步渠道**，不是默认输出方式：

1. **触发时机**：仅在第二步（设计文档）和第七步（提测）用户确认文档后询问
2. **询问方式**："是否需要同步输出一份飞书文档？"
3. **用户确认后**：调用 `feishu-doc` skill 创建飞书文档（包括 token 刷新等）
4. **用户拒绝或不回应**：不做飞书输出，流程继续
5. **飞书输出失败**：不阻断主流程，提示用户后继续
6. **飞书目录约定**：同步到飞书时，文档存放在飞书 wiki 的 `AI-docs/需求文档/` 目录下，周报存放在 `AI-docs/周报/`，总结存放在 `AI-docs/总结/`。如团队有不同命名习惯，可直接修改此约定

## 文档存放

所有文档统一存放在 `{PROJECT_ROOT}/dw-docs/` 目录下：

```
dw-docs/
├── dw-state.json              # 进度跟踪
├── dw-daily.md                # 日报记录
├── dw-index.md                # 全局索引
├── {需求名}/                  # 每个需求一个文件夹
│   ├── requirements.md        # 需求分析
│   ├── dev-design.md          # 设计文档
│   ├── cr-report.md           # AI走查报告
│   ├── unit-test-report.md    # 单元测试报告
│   ├── test-submit.md         # 提测文档
│   └── handover.md            # 移交摘要（如有）
├── archive/                   # 季度归档
│   └── YYYY-QX.md
```

## 需求移交

移交时只需要把对应的需求文件夹交给接手人即可。接手人将文件夹放入自己项目的 `dw-docs/` 目录，切换到对应分支后执行"继续 dw"，AI 自动从文件夹中的文档重建本地状态。

详见 `references/handover.md`。

## 新需求插入位置

- 新需求在 `dw-daily.md` 中按时间倒序排列，最新的在最上方

## 状态更新

- 每步完成后更新 `dw-state.json` 中对应需求的 `status` 字段

## 日报更新

每次触发关键动作时，在 `dw-daily.md` 对应需求的日期表格中追加一行记录。

### dw-daily.md 结构

文件分三个区域：

1. **顶部日报区**（每天覆盖）：用户说"输出日报"时生成，汇总当天有进展的需求
2. **Doing 区**（进行中需求）：所有未完成的需求，按最近活跃时间倒序排列
3. **Done 区**（本季度已完成）：本季度内上线/完成的需求，季度结束时归档到 `archive/`

```markdown
# Daily Log

### 📋 今日日报（MM/DD）

| 需求 | 状态 | 今日进展 |
|------|------|----------|
| 需求A | 开发中 | 完成接口联调 |
| 需求B | 已提测 | 提测文档 |
| — | — | 参加技术方案评审会 |
| — | — | 帮新同事搭开发环境 |

---

## 🚧 Doing

### 需求A
- **状态**：开发中
- **分支**：feature/xxx
- **项目管理**：[链接](url)

| 日期 | 工作内容 |
|------|----------|
| 05/14 | 完成接口联调 |
| 05/13 | 页面开发完成 |

---

## ✅ Done

### 需求B
- **状态**：已上线
- **分支**：feature/yyy
- **项目管理**：[链接](url)

| 日期 | 工作内容 |
|------|----------|
| 05/12 | 已上线 |
| 05/10 | 提测文档 |
```

### 标题层级规范

| 层级 | 用途 | 示例 |
|------|------|------|
| `#` | 文件标题，全文唯一 | `# Daily Log` |
| `##` | 分类标题 | `## 🚧 Doing`、`## ✅ Done` |
| `###` | 日报区标题 | `### 📋 今日日报（MM/DD）` |
| `###` | 需求标题 | `### 需求名` 或 `### [需求名](PRD链接)` |

> `##` 层级仅用于 Doing/Done 分类标题，需求标题用 `###` 保持视觉紧凑。

### 元信息字段说明

每个需求三级标题下方必须包含以下元信息（缺失时留空，不可省略行）：

| 字段 | 说明 | 必填 |
|------|------|------|
| **状态** | 当前需求状态 | 是 |
| **分支** | Git 分支名，跟进/零散需求填 `-` 或留空 | 是 |
| **项目管理** | 飞书项目/Jira 等项目管理链接 | 是（无则留空） |

### 写入规则

- **需求详情区（Doing / Done）**：
  - 以需求名为三级标题（`###`），有 PRD 链接的做成 markdown 链接
  - 每个需求下方有元信息（状态、分支、项目管理链接）
  - 日期表格按时间倒序排列（最新在最上方）
  - 新增日报时在对应需求的日期表格顶部插入新行
  - 新需求插入到 `## 🚧 Doing` 区的第一个位置（最新需求在最上方）

- **Doing / Done 归档规则**：
  - 需求状态变为"已上线"或"已完成"时，将该需求从 Doing 区移动到 Done 区
  - Done 区内按上线/完成时间倒序排列（最近完成的在最上方）
  - 用户说"输出日报"/"日报总结"时，自动检查所有需求状态，执行归档操作
  - 归档时保留需求的完整历史记录，不删除任何日期行

- **季度归档规则**：
  - Done 区只保留本季度的已完成需求
  - 写季度总结时（或新季度首次执行 dw 时），将上季度 Done 区内容整体移到 `dw-docs/archive/YYYY-QX.md`
  - 归档文件格式与 Done 区一致（需求标题 + 元信息 + 日期表格）
  - 归档后 dw-daily.md 的 Done 区清空，只保留本季度新完成的需求
  - archive 目录结构：`dw-docs/archive/2026-Q1.md`、`dw-docs/archive/2026-Q2.md` ...

- **顶部日报区**：
  - 用户说"输出日报"时触发生成
  - 扫描所有需求（Doing + Done）当天有记录的行，汇总为简洁表格
  - 同时扫描 `dw-state.json` 的 `misc_log` 中当天的杂项事务，追加到表格末尾（需求列和状态列填 `—`）
  - 每次生成时覆盖上一次的日报区内容（只保留最新一天）
  - 日报区位于 `# Daily Log` 和第一个 `---` 分隔线之间
  - **顺带执行归档检查**：检查所有需求状态，将已上线/已完成的从 Doing 移到 Done；若发现 dw-state.json 与 dw-daily.md 状态不一致，以 dw-state.json 为准静默修复

### 同步到 dw-state.json

日报写入 `dw-daily.md` 的同时，也更新 `dw-state.json` 中对应需求的 `daily_log` 字段（保持数据一致，便于程序化读取）。

### 周报时的轻量维护

写周报时（反正要读全量数据），顺带做一件事：

- **过期提醒**：列出 Doing 区中超过 2 周（14 天）无更新的需求，在周报末尾以"⏳ 以下需求长期无进展"形式提示用户，不做任何自动处理

> 注：不做索引一致性扫描和文件夹完整性检查——索引在每步流程中已同步维护，文件夹按流程阶段产出本就不完整，主动检查会误报。数据不一致属于流程 bug，发现时当场修即可。

## 度量埋点执行规则

在七步流程执行过程中，自动记录度量数据（详细规范见 `references/metrics.md`）：

> **⚠️ 建议规则**：度量记录有助于量化提效，建议在阶段切换时顺手记录，但不强制。遗漏时不视为执行失败。

### 自动记录时机

| 时机 | 记录内容 | 强制级别 |
|------|----------|----------|
| 进入每个步骤 | `phases.{阶段}.started_at` = 当前时间 | **MUST** |
| 用户确认通过 | `phases.{阶段}.completed_at` = 当前时间，计算 `duration_minutes` | **MUST** |
| 每次 AI 响应 | `phases.{阶段}.turns` += 1 | SHOULD |
| 用户要求修改 | `phases.{阶段}.revisions` += 1 | **MUST** |
| 用户驳回 | `phases.{阶段}.rejections` += 1 | **MUST** |
| 第一步完成 | 评估并记录 `complexity`（规模/类型/模块数） | **MUST** |
| 第五步完成 | 记录 `quality.cr_issues_total` 和 `cr_false_positives` | **MUST** |
| 第六步完成 | 记录 `quality.test_*` 和 `bugs_found` | **MUST** |
| 需求上线 | 计算 `total_duration_minutes` 和 `total_turns` | **MUST** |

### 阶段切换检查清单

每次阶段切换（用户确认通过当前步骤）时，AI 必须在同一次 dw-state.json 写入中完成以下所有操作：

1. ✅ 当前阶段 `completed_at` = 当前时间
2. ✅ 当前阶段 `duration_minutes` = completed_at - started_at（分钟，向上取整）
3. ✅ 当前阶段 `checklist_completed` = true/false
4. ✅ 下一阶段 `started_at` = 当前时间（如果立即进入下一步）
5. ✅ 第一步完成时：填写 `complexity`（size/type/modules_count）
6. ✅ 更新 `total_turns`（所有阶段 turns 之和）
7. ✅ 需求完成时：计算 `total_duration_minutes`

### 复杂度评估规则（第一步完成时必填）

| 维度 | 评估标准 |
|------|----------|
| size | S: <100行变更, M: 100-500行, L: 500-1000行, XL: >1000行 |
| type | 新功能 / 重构 / Bug修复 / 优化 |
| modules_count | 涉及的独立业务模块数（按 src/view/ 下的一级目录计） |

### 跳过阶段处理

- 无需联调（第四步）：`integration` 设为 `null`
- 跳过 CR/单测（用户明确要求跳过）：对应阶段设为 `null`
- 快速需求（如 hotfix）跳过分析/设计：对应阶段设为 `null`

### Baseline 自动建立

当 `metrics_baseline` 为 null 且已有 ≥5 个需求的 `total_duration_minutes` 不为 null 时：
1. 自动计算全局 baseline 并写入
2. 按 size 分层计算（该规模 ≥2 个样本时）
3. 在对话中告知用户"已建立效率基线"

### 阶段名映射

| 流程步骤 | metrics.phases 字段名 |
|----------|----------------------|
| 第一步：需求分析 | requirement_analysis |
| 第二步：设计文档 | design |
| 第三步：代码开发 | development |
| 第四步：接口联调 | integration |
| 第五步：AI CR | code_review |
| 第六步：单元测试 | unit_test |
| 第七步：提测 | test_submission |

### 注意事项

- 度量记录是静默操作，不需要告知用户"正在记录度量"
- 跳过的阶段（如无需联调）设为 `null`
- 如果用户在同一阶段跨天操作，`duration_minutes` 仍按实际时间差计算

### checklist_completed 校验规则

每个阶段完成时（用户确认通过），AI 自检该阶段的所有检查项是否都已执行：

| 阶段 | 校验内容 |
|------|----------|
| requirement_analysis | 10 个维度是否逐条输出了检查结论 |
| design | 交互流程图、数据流图、修改文件表格是否都已生成 |
| development | ESLint 通过、无调试代码、context 已更新 |
| code_review | 6 个维度是否逐维度输出了通过/问题数 |
| unit_test | 测试是否全部运行、覆盖率是否已采集 |
| test_submission | 所有可自动填充的字段是否已填充 |

- 全部通过 → `checklist_completed: true`
- 有遗漏 → `checklist_completed: false`，在确认点提示用户"以下检查项未完成：xxx"

## 决策原则

- **不确定的事情必须停下来问用户，不要猜**

## 文件编辑原则

- **修改已有文件时，必须使用精确替换（str_replace），禁止整文件覆盖（fs_write）**
- `fs_write` 仅用于新建文件
- 即使只改一行代码，也要用 str_replace 精确定位并替换，不要重写整个文件
- 这条规则适用于所有文件类型：代码文件、配置文件、文档文件

## 上下文传递

- 每步生成的关键信息（需求名、分支名、文档链接、接口文档地址等）需在后续步骤中自动引用，不要重复询问用户
- 当获取到新的关键信息时（如用户提供接口文档地址），必须立即回填到之前已创建的相关文档中（如设计文档的元信息表格），不要等用户提醒
- 如果会话中断后恢复，先读取 `dw-state.json` 中该需求的 `context` 字段获取已有上下文，从断点继续

### context 字段维护规则

`dw-state.json` 中每个需求的 `context` 字段是步骤间数据传递的显式载体，减少对 AI 对话记忆的依赖：

| 字段 | 写入时机 | 用途 |
|------|----------|------|
| `prd_summary` | 第一步需求分析完成 | 后续步骤快速了解需求背景 |
| `api_doc_url` | 用户提供接口文档时 | 第三步开发、第四步联调引用 |
| `design_decisions` | 第二步设计文档完成 | 第三步开发遵循、第五步 CR 对照 |
| `affected_modules` | 第一步/第二步完成 | 第五步 CR 确定走查范围、第六步确定测试范围 |
| `tech_highlights` | 第二步设计文档完成 | 索引更新、周报/总结引用 |
| `integration_notes` | 第四步联调完成 | 提测文档引用 |

**规则**：
- 每个步骤完成时，必须将该步骤产出的关键信息写入 `context`
- 进入新步骤时，先读取 `context` 获取前序步骤的关键信息
- `context` 中的值只追加/更新，不删除（保留完整历史）
- 会话中断恢复时，`context` 是恢复上下文的首要数据源

## 多需求并行

- 同一时间可能有多个需求在不同阶段，每个需求独立跟踪
- 用户切换需求时，通过需求名或分支名定位到 `dw-state.json` 中对应的条目
- `dw-daily.md` 中同一天可以有多个需求的记录

## 中断与恢复

- 用户可以在任意步骤暂停，后续通过"继续 dw"恢复
- **分支名是需求的唯一标识**，所有恢复逻辑都基于当前 Git 分支名

### 分支匹配逻辑（按优先级）

用户说"继续 dw"时，执行以下匹配：

1. **本地 dw-state.json 中有该分支** → 读取 `context` 和 `status`，直接从断点继续
2. **本地有移交文档**（`dw-docs/` 下存在对应需求文件夹且含 `handover.md`，其中"Git 分支"字段匹配当前分支）→ 从移交文档重建 dw-state 条目，填充 context，继续
3. **以上都未匹配** → 如果当前在 main/master 上，读取 dw-state.json 列出进行中的需求让用户选择；否则提示"该分支未关联任何需求记录，是否作为新需求开始？"

### 从移交文档重建状态（路径 2）

当本地 dw-state.json 中没有该分支，但找到了匹配的移交文档时，自动执行：

1. 在 `dw-state.json` 的 `requirements` 数组中创建该需求条目
2. 从移交文档提取并填充：`name`、`branch`、`status`、`pm_url`、`prd_source`、`documents`
3. 填充 `context` 字段：从移交文档提取 prd_summary、affected_modules、tech_highlights、design_decisions
4. `daily_log` 当天追加"接手自 [移交人]"，同时写入 `dw-daily.md`
5. 更新索引条目状态
6. 输出当前进度摘要：

```
已恢复上下文 ✓
- 需求：[需求名]
- 当前阶段：第X步（xxx）
- 待办事项：
  - [ ] xxx
- 已知风险：xxx

准备从第X步继续，确认开始？
```

## 变更同步规则

修改规范文件（`SKILL.md`、`references/*.md`）后，顺手 grep 变更涉及的关键词（如状态值、文件名、触发词），确认无残留引用。影响范围通常包括 `README.md`、`REPORT.md`、其他 `references/*.md` 的交叉引用。

## 自我学习

AI 在对话中自然识别有价值的信息并闭环，不搞额外的 feedback log。

### 识别信号

以下情况出现时，AI 主动问用户"要不要把这个沉淀为规范？"：

| 场景 | 信号 | 示例 |
|------|------|------|
| 用户纠正了 AI 的做法 | AI 方案被否定，用户给出正确做法 | "不要用 moment，用 dayjs" |
| 用户补充了 AI 没覆盖的内容 | 用户主动添加 AI 遗漏的要素 | "这里还要加一个 loading 状态" |
| 同一类问题第二次出现 | AI 犯了和上次一样的错 | 又忘了加空值保护 |
| 用户表达了偏好 | "我喜欢这样做"/"别这样做" | "组件命名用大驼峰" |
| 用户跳过了某个步骤 | 该步骤不必要或条件不对 | "跳过单测，列表页不需要" |
| 用户改了 AI 输出的格式/结构 | 文档/代码组织不符合预期 | 重新调整了设计文档章节 |
| 发现了工具/平台限制的 workaround | 以后可以复用 | "文件是 CRLF，脚本要按行处理" |
| 用户提出了更高效的工作流 | 流程改进建议 | "设计文档和需求分析可以合并" |

### 闭环动作

用户确认后，直接修改对应文件：

- 编码/技术类 → `coding-standards` 或对应 `references/*.md`
- 流程类 → `SKILL.md` 或 `general-rules.md`
- 个人偏好类 → `LEARNING.md` 的"用户偏好"区域

改完后在 `LEARNING.md` 的"已沉淀的规范更新"表中记一行，方便追溯。

### 不做的事

- 不记 feedback log
- 不搞统计分析（修改率、驳回率等）
- 不定期回顾
- 不在对话中反复提醒"学习机制已启动"

本质：**发现 → 问 → 改规范 → 生效**，四步闭环。
