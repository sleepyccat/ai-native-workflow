# Bugfix 模式

## 概述

用于生产环境缺陷修复的轻量开发流程。相比完整七步流程，跳过需求分析和设计文档，聚焦快速定位和修复。

## 触发条件

以下方式进入 bugfix 模式：
- "修复 xxx" / "bugfix xxx" / "fix xxx" + 缺陷描述
- "开启 dw" + 缺陷描述（含"缺陷"/"bug"/"修复"/"fix"/"hotfix"关键词时自动识别）

## 流程（四步）

```
触发 → 问题记录 + 创建分支 → 代码修复 → AI CR → 提测
```

### 第一步：问题记录

- 创建文件夹 `dw-docs/{缺陷名}/`
- 生成 `bugfix.md`，内容包含：
  - 缺陷描述（用户提供的原始描述）
  - 复现步骤（如有）
  - 影响范围
  - 根因分析（定位后补充）
  - 修复方案（简述）
- 创建 Git 分支：`feature/fix-{缺陷英文简称}`
- 更新 `dw-state.json`：记录需求，类型标记为 `bugfix`
- 更新日报 `dw-daily.md`

### 第二步：代码修复

- 基于问题定位直接修复代码
- 不主动生成设计文档（用户需要时手动要求）
- 完成后更新 `bugfix.md` 中的根因分析和修复方案
- ESLint 通过、无调试代码

### 第三步：AI CR

- 引用：`cr-general` skill（轻量模式）
- 聚焦：回归风险、边界 case、是否引入新问题
- 输出走查报告到 `dw-docs/{缺陷名}/cr-report.md`

### 第四步：提测

- 引用：`test-submission` skill
- 简化版提测文档，重点：修了什么、怎么验证、影响范围
- 输出到 `dw-docs/{缺陷名}/test-submit.md`
- 飞书同步询问：用户确认提测文档后，询问是否需要同步输出飞书文档

## 状态流转

```
修复中 → AI CR中 → 已提测 → 已上线
```

## 日报格式

复用现有日报格式，标题加 `【bugfix】` 前缀：

```markdown
### 【bugfix】{缺陷名称}
- **状态**：修复中
- **分支**：`feature/fix-{英文简称}`
- **项目管理**：{bug 单链接，如有}

| 日期 | 工作内容 |
|------|----------|
| MM/DD | 定位问题并修复，提测 |
```

## bugfix.md 模板

```markdown
# 缺陷修复：{缺陷名称}

## 缺陷描述

{用户提供的原始描述}

## 复现步骤

1. ...
2. ...

## 影响范围

- 影响页面/模块：
- 影响用户：

## 根因分析

{定位后补充}

## 修复方案

{简述修复内容}

## 修复文件清单

| 文件 | 修改内容 |
|------|----------|
| ... | ... |
```

## 与其他模式的区别

| 维度 | 开发模式 | 跟进模式 | Bugfix 模式 |
|------|---------|---------|------------|
| Git 分支 | feature/ | 无 | feature/fix- |
| 需求分析 | ✅ | ✅ | ❌ |
| 设计文档 | ✅ | ❌ | 用户手动要求时才做 |
| 代码开发 | ✅ | ❌ | ✅ |
| AI CR | ✅ | ❌ | ✅（轻量） |
| 单元测试 | ✅ | ❌ | 用户手动要求时才做 |
| 提测 | ✅ | ❌ | ✅（简化版） |

## dw-state.json 记录格式

```json
{
  "name": "{缺陷名称}",
  "type": "bugfix",
  "status": "修复中",
  "branch": "feature/fix-{英文简称}",
  "startDate": "YYYY-MM-DD",
  "bugLink": "{bug 单链接，可选}"
}
```
