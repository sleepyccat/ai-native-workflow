# RL 训练闭环：反馈驱动的持续优化

## 核心理念

将用户在流程中的每次反馈（确认/修改/驳回）视为强化学习的 reward signal，结构化记录到飞书文档中。AI 在每次执行时读取历史反馈数据，调整输出策略，实现"越用越好"。

## 反馈日志

### 存储位置

- **飞书后端**：飞书 `AI-docs/feedback_log` 文档（如不存在则自动创建）
- **本地后端**：`{SKILLS_DIR}/daily-workflow/output/{项目名}/dw-feedback.md`

### 数据结构

每条反馈记录一行：

| 日期 | 需求名 | 步骤 | AI 输出摘要 | 用户反馈 | 反馈类型 | 调整动作 | 是否已沉淀 |
|------|--------|------|-------------|----------|----------|----------|------------|

字段说明：
- **步骤**：第几步 + 具体环节（如"第一步-需求分析"、"第三步-组件选型"、"第五步-CR走查"）
- **AI 输出摘要**：AI 当时给出的方案/建议的一句话摘要
- **用户反馈**：用户的具体反馈内容
- **反馈类型**：
  - `确认` — 用户直接接受，正向奖励
  - `修改` — 用户接受但做了调整，弱负向信号
  - `驳回` — 用户完全否定，强负向信号
- **调整动作**：AI 根据反馈做了什么调整（如"改用 xxx 方案"、"调整了 xxx 格式"）
- **是否已沉淀**：该反馈是否已转化为规范更新（是/否）

### 反馈类型判定规则

用户的表达方式多样，以下规则帮助 AI 准确分类：

| 用户行为/表达 | 判定为 | 说明 |
|--------------|--------|------|
| "确认"/"没问题"/"继续"/"可以" | 确认 | 无修改直接通过 |
| "改成 xxx"/"用 xxx 替代"/"这里换成 xxx" | 修改 | 接受方向但调整细节 |
| "加上 xxx"/"还需要 xxx"/"漏了 xxx" | 补充 | AI 未覆盖的内容 |
| "跳过"/"不用管"/"这步不需要"/"删掉这条" | 驳回 | 完全否定该项 |
| "这不是问题"/"误报"/"不算 bug" | 驳回 | 否定 AI 的判断 |
| "不要紧"/"先不管"/"低优先级以后再说" | 驳回（弱） | 记录但不触发高优标记 |
| 用户手动修改了 AI 输出的代码/文档 | 修改 | 通过 diff 检测 |
| 用户对严重程度/优先级有异议 | 修改 | 记录原级别和新级别 |

**边界情况处理**：
- 用户说"先这样吧"但语气犹豫 → 标记为 `确认`，不过度解读
- 用户跳过整个步骤 → 标记为 `驳回`（强信号）
- 用户部分接受部分修改 → 接受的部分标记 `确认`，修改的部分单独记录为 `修改`

### 记录时机

在七步流程的每个确认点自动记录：

| 确认点 | 记录内容 |
|--------|----------|
| 需求分析确认 | 问题清单的采纳情况（哪些被确认、哪些被修改、哪些被忽略） |
| 设计文档确认 | 设计方案的采纳情况（组件拆分、数据结构、技术选型） |
| 代码开发确认 | 代码实现的采纳情况（用户要求的修改点） |
| 接口联调确认 | 联调方案的采纳情况 |
| AI CR 确认 | 走查问题的处理情况（哪些修复、哪些忽略、哪些误报） |
| 单元测试确认 | 单元测试的覆盖情况和失败用例处理 |
| 提测确认 | 提测文档的采纳情况 |

### 记录规则

- 只记录有实质反馈的确认点（用户直接说"确认"不记录细节，只标记"确认"类型）
- 用户修改了 AI 输出时，记录修改前后的差异
- 用户驳回时，记录驳回原因和最终采用的方案

## 策略优化

### 优化触发条件

| 条件 | 优化动作 |
|------|----------|
| 同一类问题被 `修改` ≥ 2 次 | 在当前步骤确认点提出规范更新建议 |
| 同一类问题被 `驳回` ≥ 1 次 | 立即标记为高优先级优化项，下次执行时主动规避 |
| 某个模式连续 `确认` ≥ 3 次 | 固化为最佳实践，记录到对应规范文件 |
| CR 误报率 > 30%（某维度） | 建议调整该维度的检查阈值或移除检查项 |
| 单元测试遗漏率 > 20% | 建议补充对应维度的测试场景 |

### 优化执行流程

1. **读取反馈日志**：每次执行流程前，读取 `feedback_log` 中与当前步骤相关的历史反馈
2. **识别模式**：统计同类反馈的频次和趋势
3. **调整策略**：
   - 短期调整：在当前会话中直接应用（如"上次你说 xxx 不需要，这次我跳过了"）
   - 长期沉淀：达到触发条件时，提出规范更新建议，用户确认后更新 references 文件
4. **标记已沉淀**：规范更新后，将对应的反馈记录标记为"已沉淀"

### 反馈分析维度

按以下维度聚合分析反馈数据：

| 维度 | 分析内容 | 优化方向 |
|------|----------|----------|
| 按步骤 | 哪个步骤的修改/驳回率最高 | 优化该步骤的规范或执行策略 |
| 按类型 | 代码规范类/逻辑类/文档格式类哪类反馈最多 | 针对性优化对应规范 |
| 按模块 | 哪个业务模块的反馈最多 | 补充或调整模块专项规范 |
| 按时间 | 反馈趋势是收敛还是发散 | 评估优化效果 |

## 用户偏好学习

反馈日志中隐含的用户偏好也会被提取和记录：

- **编码偏好**：用户反复修改的代码风格（如偏好某种组件写法）
- **文档偏好**：用户对文档详略程度的偏好（如"设计文档不用写这么细"）
- **沟通偏好**：用户对 AI 交互方式的偏好（如"别问这么多，直接做"）
- **决策偏好**：用户在技术选型上的倾向（如"能用 antd 原生的就不引第三方"）

### 偏好分类与沉淀路径

提取到的偏好需要区分"个人偏好"和"团队规范"：

| 类型 | 判定标准 | 沉淀位置 | 示例 |
|------|----------|----------|------|
| 个人偏好 | 仅影响交互体验，不涉及代码质量 | 各 skill 的 `LEARNING.md` | "别问这么多直接做"、"设计文档偏简洁" |
| 团队规范 | 影响代码质量/一致性，适用于所有成员 | 对应的 `references/*.md` | "能用 antd 原生就不引第三方"、"接口必须有 loading 状态" |

**沉淀流程**：
1. 首次出现 → 记录到 `feedback_log` 底部的"用户偏好"区域
2. 同类反馈 ≥ 3 次 → AI 提出沉淀建议，询问"这条规则是个人偏好还是团队规范？"
3. 用户确认为团队规范 → 沉淀到对应 references 文件（所有人可见）
4. 用户确认为个人偏好 → 留在 LEARNING.md（仅当前用户生效）

提取到的偏好记录到 `feedback_log` 底部的"用户偏好"区域，格式：

```
## 用户偏好
- [编码/团队] 偏好使用 antd 原生组件，避免引入第三方 UI 库（来源：第三步反馈 x3）→ 已沉淀到 references/tech-stack.md
- [文档/个人] 设计文档偏简洁，不需要详细的状态流转图（来源：第二步反馈 x2）
- [沟通/个人] 问题清单不需要逐条确认，一次性列出即可（来源：第一步反馈 x2）
```

## 定期回顾

- **周度**：写周报时，自动附带本周反馈摘要（确认率、主要修改点）
- **季度**：写季度总结时，输出反馈趋势分析（优化效果、收敛情况）
- **里程碑**：每完成 10 个需求，输出一次综合反馈分析报告
