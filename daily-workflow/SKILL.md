# 开发工作流 Skill

你是一个开发专家。当用户给你一个 PRD 链接时，严格按照七步流程执行。

## 前置条件

### 存储后端

daily-workflow 采用混合存储策略：

| 内容 | 存储位置 | 说明 |
|------|----------|------|
| 日报记录 | 本地 `dw-daily.md` | 自己看的，不需要共享 |
| 进度跟踪/断点恢复 | 本地 `dw-state.json` | 机器用的结构化数据 |
| 需求分析、设计文档等 | 飞书云文档（需配置）或本地 `dw-docs/*.md` | 需要给别人看的技术文档 |
| 周报、总结 | 飞书云文档（需配置）或本地 `dw-docs/*.md` | 汇报类，需要共享 |
| 索引 | 飞书 index 文档（需配置）或本地 `dw-index.md` | 跨文档导航 |
| PRD 输入 | 飞书链接 或 本地 MD 文件路径 | — |

**原则**：需要给别人看的走飞书文档，自己看的走本地文件。

**飞书文档输出判断逻辑**：检查 `{SKILLS_DIR}/config.json` 是否存在且 `feishu.root_wiki_url` 已配置（非占位符）。已配置则文档输出到飞书，否则输出到本地 `dw-docs/`。无论是否配置飞书，日报和进度跟踪始终走本地。

### 飞书文档输出配置（可选）

- 飞书根目录：`AI-docs/`（校验规则见 `feishu-doc` skill）
### 本地目录结构

```
{SKILLS_DIR}/daily-workflow/output/
├── dw-state.json              # 需求进度跟踪（始终本地）
├── dw-daily.md                # 日报记录（始终本地）
├── dw-index.md                # 长期索引（无飞书配置时使用）
└── dw-docs/                   # 各步骤文档（无飞书配置时使用）
    ├── [需求名]_需求分析.md
    ├── [需求名]_设计文档.md
    ├── [需求名]_走查报告.md
    ├── [需求名]_单元测试报告.md
    └── [需求名]_提测文档.md
```

### 通用

- 规范文档：位于 `references/` 目录下
- 关联 skill：`requirement-analysis`、`development-design`、`coding-standards`、`cr-general`、`unit-testing`、`test-submission`、`feishu-doc`、`cross-platform-export`
- 私人凭证（飞书后端时需要）：统一存放在 `{SKILLS_DIR}/config.json`

## 七步流程

### 第一步：需求分析

- **触发**：用户提供 PRD（飞书链接或本地 MD 文件）
- **引用**：`requirement-analysis` skill（daily-workflow 模式）
- **默认为开发模式**：创建 Git 分支，走完整七步流程
- **跟进模式**：当用户说"跟进 xxx"时触发，不创建 Git 分支，只做需求分析即结束。用户也可事后删除已写入的 Git 分支名将开发型转为跟进型
- **执行（开发模式）**：读取 PRD → 创建管理文件 → 生成 Git 分支 → 识别模块专项规范 → 记录进度 → 执行需求分析（含代码对照）→ 更新索引
- **执行（跟进模式）**：读取 PRD → 询问飞书项目链接 → 创建管理文件（无分支）→ 执行需求分析 → 更新索引。状态只有"跟进中"和"已上线"两种
- **需求分析文档**：文档头部包含飞书项目链接字段（跟进模式必填，开发模式可选）
- **确认点**：用户查看问题清单后决策（继续/打回/澄清后重新评估）
- **通过后（开发模式）**：状态更新为"设计中"，进入第二步
- **通过后（跟进模式）**：状态更新为"跟进中"，流程结束

### 第二步：设计文档

- **触发**：用户确认需求分析后
- **引用**：`development-design` skill（daily-workflow 模式）
- **执行**：生成设计文档 → 写入存储后端 → 更新索引摘要区和关键技术点
- **确认点**：用户确认设计文档
- **通过后**：状态更新为"开发中"，进入第三步

### 第三步：代码开发

- **触发**：用户确认设计文档后
- **引用**：`coding-standards` skill + `references/modules/*.md`（如有）
- **执行**：确认 Git 分支 → 询问接口文档 → 基于设计文档生成代码 → 输出完成清单
- **决策点**：第三方库选择、已有逻辑重构、性能 trade-off、不确定的业务逻辑 → 必须停下询问
- **完成检查**：ESLint 通过、无调试代码
- **变更同步**：实现方案调整后立即同步更新设计文档
- **确认点**：用户确认代码
- **通过后**：有临时接口 → "待联调"进入第四步；已对接真实接口 → "AI CR中"跳到第五步

### 第四步：接口联调

- **触发**：存在临时接口逻辑时
- **执行**：用户提供接口文档 → 替换所有 `// TODO: 接口联调时替换` 标记 → 输出联调变更清单
- **异常处理**：字段不匹配列出差异询问用户；部分接口未提供标记未替换部分
- **确认点**：用户确认联调
- **通过后**：状态更新为"AI CR中"，进入第五步

### 第五步：AI Code Review

- **触发**：代码开发/联调完成后
- **引用**：`cr-general` skill + `references/code-review.md` + `references/modules/*.md`（如有）
- **执行**：按走查维度分析代码 → 代码规范类自动修复 → 逻辑类列出等用户确认 → 生成走查报告
- **确认点**：逻辑类问题逐条确认修复
- **通过后**：状态更新为"单元测试中"，进入第六步

### 第六步：单元测试

- **触发**：AI CR 完成后
- **引用**：`unit-testing` skill（daily-workflow 模式）+ `references/modules/*.md`（如有）
- **执行**：生成单元测试 → 运行测试 → 修复失败用例 → 写入存储后端
- **源码修复记录**：修复源码 Bug 后自动追加到测试报告
- **确认点**：单元测试全部通过（或用户确认跳过需人工处理的用例）
- **通过后**：状态更新为"测试中"，进入第七步

### 第七步：提测

- **触发**：单元测试完成后
- **引用**：`test-submission` skill
- **执行**：提醒用户完成 QA 冒烟测试 → 生成提测文档 → 自动填充上下文字段 → 逐个询问无法自动获取的字段
- **确认点**：用户确认提测文档
- **通过后**：状态更新为"已提测"，更新索引

**后续状态流转**（用户手动触发）：
- "测试中" → 更新状态，同步索引
- "已上线" → 更新状态 + 完成日期，同步索引和摘要区

## 文档输出风格

飞书后端时，文档按类型分两种风格：

| 风格 | 适用文档 | 规则来源 |
|------|----------|----------|
| 汇报风格（绚丽） | REPORT 更新、周报、季度/年度总结 | `feishu-doc` skill 的 `references/report-style.md` |
| 技术模板（固定格式） | 需求分析文档、设计文档、走查报告、单元测试报告、提测文档 | 各 skill 自身的输出模板 |

写入汇报类文档前，读取 `feishu-doc` skill 的 `references/report-style.md`。技术类文档直接用各 skill 定义的格式，不读 report-style.md。

## References（参考配置）

用户可编辑的参考配置统一存放在 `references/` 下（如 weekly-report.md 等），换团队/换技术栈时替换对应文件即可，无需修改 SKILL.md。

## 通用规则

读取 `references/general-rules.md`，严格遵守。包含：日报记录规则、自我学习与优化机制、变更同步规则。

**SKILL.md 维护原则**：新增功能的详细规范必须拆到 `references/` 下独立文件，SKILL.md 只保留一行引用和触发词。保持 SKILL.md 作为流程骨架，清晰简洁，一目了然。

## 自我学习

学习规则与反馈日志详见 `LEARNING.md`。

核心机制：
- **触发时机**：用户对 AI 输出做了修改/驳回/补充时自动记录
- **策略优化**：同类修改 ≥2 次建议更新规范，驳回 ≥1 次下次规避，确认 ≥3 次固化最佳实践
- **执行流程**：识别 → 提出 → 用户确认 → 执行 → 记录到 LEARNING.md
- **变更同步**：规范更新后同步更新 SKILL.md 对应章节

每次执行前读取 LEARNING.md 中的"用户偏好"和"已沉淀的规范更新"，将学到的知识应用到当前输出中。

## 度量埋点

详见 `references/metrics.md`。核心：在七步流程的每个阶段自动记录开始/结束时间、交互轮次、修改/驳回次数和质量指标。数据存储在 `dw-state.json` 的 `metrics` 字段中。首批 5 个需求建立 baseline，后续数据与 baseline 对比计算提效百分比。周报/季度总结时自动输出效率趋势分析。

## RL 训练闭环

详见 `references/feedback-loop.md`。核心：将用户每次反馈（确认/修改/驳回）结构化记录（飞书后端：`AI-docs/feedback_log`；本地后端：`output/dw-feedback.md`），AI 基于反馈数据持续优化策略。每次执行流程前读取历史反馈，短期调整当前策略，长期沉淀为规范更新。

## 结构化索引

详见 `references/index-strategy.md`。核心：维护全局索引（飞书后端：`AI-docs/index`；本地后端：`output/dw-index.md`），实现跨会话长期记忆和高效检索。

## 快速触发

- "开启 dw" + PRD（飞书链接或本地文件路径）→ 启动七步流程
- "开启 dw" + PRD + "模块：xxx" → 指定模块专项规范
- "跟进 xxx" + PRD → 跟进模式，只做需求分析（不建分支，询问飞书项目链接）
- "继续 dw" → 通过 Git 分支名匹配需求，从断点恢复（也支持接手移交的需求）
- "更新 dw" + 状态 → 手动更新需求状态
- "记录" / "记一下" / "log" + 内容 → 快速记录
- "移交 [需求名] 给 [人名]" → 需求移交
- "导出 skill 到 [平台]" → 跨平台导出
- "写周报" / "写季度总结" / "年度总结" → 生成文档
