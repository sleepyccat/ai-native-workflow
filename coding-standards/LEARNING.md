# 编码规范 Skill 学习机制

## 零、首次执行引导

> **AI 执行规则**：每次执行 skill 时检查下方日志表是否为空。如果为空（首次使用），在输出规范建议后主动告知用户：
>
> "💡 学习机制已启动：我会记录你对编码规范建议的反馈用于持续优化规范库。你可以随时查看 `LEARNING.md` 了解我学到了什么。"
>
> 此提示只在日志表为空时触发一次。

**记录执行检查清单**（AI 自检）：
- [ ] 用户否定了某条规范建议？→ 记录到日志表（驳回）
- [ ] 用户补充了新的编码规范？→ 记录到日志表（补充）
- [ ] 用户修改了规范的适用范围？→ 记录到日志表（修改）
- [ ] 用户直接接受了规范建议？→ 标记确认

## 一、反馈触发点

| 场景 | 记录什么 | 反馈类型 |
|------|---------|---------|
| 用户纠正了 AI 给的代码示例 | 哪条规范、AI 怎么写的、用户改成什么 | 修改 |
| 用户说"我们不用这种写法"/"不对" | 哪条规范、用户期望的写法 | 驳回 |
| 用户问的写法在规范中没有覆盖 | 缺失的规范项、AI 临时给的答案 | 补充 |
| 用户对代码风格检查结果提出异议 | 哪条检查项、AI 判定、用户看法 | 驳回 |
| 用户直接接受了 AI 给的代码示例 | 哪条规范、什么场景 | 确认 |
| 被引用时（daily-workflow 第三步）用户修改了生成的代码 | 哪条规范被违反、用户为什么改 | 修改 |

## 二、反馈记录

### 日志表

| 日期 | 场景 | AI 输出 | 用户反馈 | 反馈类型 | 调整动作 | 是否已沉淀 |
|------|------|---------|----------|----------|----------|------------|

反馈类型：
- `确认` — 用户直接接受
- `修改` — 用户接受但调整了
- `驳回` — 用户完全否定
- `补充` — 用户添加了 AI 未覆盖的内容

### 记录规则

- 只记录有实质反馈的交互（用户直接说"好的"只标记为确认，不记详情）
- 用户修改了 AI 输出时，记录修改前后的差异
- 用户驳回时，记录驳回原因和最终采用的写法
- 同一规范条目被多次反馈时，在日志表中追加行，便于统计

## 三、策略优化

| 条件 | 动作 |
|------|------|
| 同一规范条目被 `修改` ≥ 2 次 | 在下次执行时提出规范更新建议，询问用户是否更新 SKILL.md |
| 同一规范条目被 `驳回` ≥ 1 次 | 立即标记为高优先级，下次执行主动规避该写法 |
| 某个写法模式连续被 `确认` ≥ 3 次 | 固化为最佳实践，建议更新到 SKILL.md 对应章节 |
| 缺失规范被 `补充` ≥ 2 次 | 建议新增规范章节到 SKILL.md |

### 优化执行流程

1. **识别**：在规范查询、风格检查、代码生成过程中发现可优化点
2. **提出**：向用户描述问题和优化方案，说明影响 SKILL.md 的哪个章节
3. **确认**：等待用户确认，不自行修改
4. **执行**：用户确认后，更新 SKILL.md 对应章节
5. **记录**：将变更记录到下方"已沉淀的规范更新"表中，并将日志表中对应记录标记为"已沉淀"
