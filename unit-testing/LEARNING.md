# 单元测试 Skill 学习机制

## 零、首次执行引导

> **AI 执行规则**：每次执行 skill 时检查下方日志表是否为空。如果为空（首次使用），在测试全部通过后主动告知用户：
>
> "💡 学习机制已启动：我会记录你对测试用例的反馈（删除/修改/补充场景）用于持续优化测试策略。你可以随时查看 `LEARNING.md` 了解我学到了什么。"
>
> 此提示只在日志表为空时触发一次。

**记录执行检查清单**（AI 自检）：
- [ ] 用户删除了某个测试用例？→ 记录到日志表（驳回）
- [ ] 用户补充了 AI 未覆盖的测试场景？→ 记录到日志表（补充）
- [ ] 用户修改了测试策略（Mock 方式/断言方式）？→ 记录到日志表（修改）
- [ ] 用户直接接受了测试结果？→ 标记确认

## 一、反馈触发点

| 场景 | 记录什么 | 反馈类型 |
|------|---------|---------|
| 用户删除了某个测试用例 | 哪个文件、什么用例、为什么不需要 | 驳回 |
| 用户添加了 AI 未生成的测试用例 | 新的测试场景、属于哪个维度 | 补充 |
| 用户修改了 AI 生成的测试代码 | 哪个用例、AI 写的、用户改成什么 | 修改 |
| 用户说"这个文件不用测" | 哪个文件、原因 | 驳回 |
| 用户直接接受了所有测试 | 哪个文件、什么场景 | 确认 |
| 测试修复 3 次仍未通过 | 哪个用例、失败原因、最终处理方式 | 补充 |
| AI 修复了源码 Bug | 哪个文件、什么 Bug | 确认 |

## 二、反馈记录

### 日志表

| 日期 | 场景 | AI 输出 | 用户反馈 | 反馈类型 | 调整动作 | 是否已沉淀 |
|------|------|---------|----------|----------|----------|------------|

反馈类型：
- `确认` — 用户直接接受
- `修改` — 用户接受但调整了
- `驳回` — 用户完全否定
- `补充` — 用户添加了 AI 未覆盖的内容

### 记录规则

- 用户删除测试用例时，记录原因 — 可能是用例本身不合理，也可能是场景不适用
- 用户添加的测试用例是强信号，必须记录 — 说明测试生成策略有遗漏
- 3 次修复仍未通过的用例需重点记录 — 可能是 mock 策略或框架配置有问题

## 三、策略优化

| 条件 | 动作 |
|------|------|
| 同类测试用例被驳回（删除）≥ 2 次 | 建议将该类场景从不生成列表中排除或降低优先级 |
| 新测试场景被补充 ≥ 2 次 | 建议新增到测试生成策略的覆盖维度中 |
| 测试代码被修改 ≥ 2 次 | 建议调整该类场景的 mock 策略或断言方式 |
| 某类测试连续被确认 ≥ 3 次 | 固化为高价值测试模式，标记为核心覆盖项 |
| 3 次修复未通过率 > 15% | 建议调整 mock 策略或更新 testing-framework.md 配置 |

### 优化执行流程

1. **识别**：在测试生成或修复过程中发现可优化点
2. **提出**：向用户描述问题和优化方案，说明影响 SKILL.md 的哪个策略或 references/testing-framework.md 的哪个配置
3. **确认**：等待用户确认，不自行修改
4. **执行**：用户确认后，更新 SKILL.md 对应策略或 testing-framework.md 配置
5. **记录**：将变更记录到下方"已沉淀的规范更新"表中，并将日志表中对应记录标记为"已沉淀"
