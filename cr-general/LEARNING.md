# 代码走查 Skill 学习机制

## 零、首次执行引导

> **AI 执行规则**：每次执行 skill 时检查下方日志表是否为空。如果为空（首次使用），在生成走查报告后主动告知用户：
>
> "💡 学习机制已启动：我会记录你对 CR 问题的处理（修复/忽略/误报标记）用于持续优化检查精准度。你可以随时查看 `LEARNING.md` 了解我学到了什么。"
>
> 此提示只在日志表为空时触发一次。

**记录执行检查清单**（AI 自检）：
- [ ] 用户忽略了某条 CR 问题？→ 记录到日志表（驳回）
- [ ] 用户标记某条为误报？→ 记录到日志表（驳回，强信号）
- [ ] 用户按不同方案修复？→ 记录到日志表（修改）
- [ ] 用户添加了 AI 未发现的问题？→ 记录到日志表（补充）
- [ ] 用户直接接受了 CR 结果？→ 标记确认

## 一、反馈触发点

| 场景 | 记录什么 | 反馈类型 |
|------|---------|---------|
| 用户忽略了某条 CR 问题（未修复） | 哪个维度、什么问题、为什么忽略 | 驳回 |
| 用户手动添加了 AI 未发现的问题 | 新的问题模式、属于哪个维度 | 补充 |
| 用户对 P 级别有异议 | 哪条问题、AI 定级、用户定级 | 修改 |
| CR 报告后用户修改了代码但不是按 AI 建议改的 | 哪条建议、用户实际改法 | 修改 |
| 用户说"这不是问题"（误报） | 哪个维度、什么检查项 | 驳回 |
| 用户直接接受了 CR 结果 | 哪个维度、什么场景 | 确认 |
| 用户要求新增专项检查维度 | 维度名称、检查场景 | 补充 |

## 二、反馈记录

### 日志表

| 日期 | 场景 | AI 输出 | 用户反馈 | 反馈类型 | 调整动作 | 是否已沉淀 |
|------|------|---------|----------|----------|----------|------------|

反馈类型：
- `确认` — 用户直接接受
- `修改` — 用户接受但调整了
- `驳回` — 用户完全否定
- `补充` — 用户添加了 AI 未覆盖的内容

### 记录规则

- 只记录有实质反馈的交互
- 用户忽略问题时，记录忽略原因（"不是问题"/"现在不想改"/"低优先级"等）
- 误报是强信号，必须记录——误报意味着检查项本身有问题
- 用户按不同方案修复时，记录差异，用于学习更优的修复建议
- 用户添加新问题时，记录问题模式，用于扩展检查清单

## 三、策略优化

| 条件 | 动作 |
|------|------|
| 同一检查项被 `驳回`（误报/忽略）≥ 2 次 | 建议调整该检查项的判定条件或移除 |
| 新问题模式被 `补充` ≥ 2 次 | 建议新增检查项到 SKILL.md 对应维度 |
| P 级别被 `修改` ≥ 2 次 | 建议调整该类问题的默认定级规则 |
| 某个维度连续被 `确认` ≥ 3 次 | 固化为高价值维度，标记为核心检查项 |
| 某维度误报率 > 30% | 建议调整该维度的检查阈值或细化检查条件 |

### 优化执行流程

1. **识别**：在代码走查过程中发现可优化点
2. **提出**：向用户描述问题和优化方案，说明影响 SKILL.md 的哪个维度/检查项
3. **确认**：等待用户确认，不自行修改
4. **执行**：用户确认后，更新 SKILL.md 对应维度或检查项
5. **记录**：将变更记录到下方"已沉淀的规范更新"表中，并将日志表中对应记录标记为"已沉淀"
