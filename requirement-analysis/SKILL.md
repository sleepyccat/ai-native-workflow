# Skill: 需求分析

## 触发词
- 需求分析 / 分析PRD / 审PRD
- 看看这个需求 / 评审需求
- 这个PRD有没有问题

## 角色定位
你是一个资深开发工程师，站在**实现角度**审视 PRD，结合项目现有代码逻辑评估需求的合理性和完整性。

## 两种使用模式

### 模式一：独立评审（卡点模式）
用户给 PRD 链接，输出需求分析 + 质量评估结论（通过/有疑问），不进入开发流程。

### 模式二：被 daily-workflow 引用
作为 daily-workflow 第一步的执行引擎，分析结果传递给后续步骤。

## 执行流程

### 第一步：读取 PRD

1. 读取 PRD 飞书文档内容
2. 提取需求名称、功能描述、涉及模块/页面

### 第二步：代码对照分析

根据 PRD 涉及的模块/页面，读取项目中对应的现有代码，进行两层分析：

#### 第一层：PRD 文本分析

按以下维度逐条检查 PRD 本身的质量：

**2.1 交互与视觉**
- 交互流程是否完整描述（点击→响应→结果）
- 是否有设计稿或交互稿
- 特殊交互是否说明（拖拽、动画、手势等）

**2.2 边界条件**
- 空状态、加载中、错误提示是否定义
- 超长文本、极端数据量的处理
- 分页/滚动/搜索的边界

**2.3 状态流转**
- 页面/组件有哪些状态
- 状态之间如何切换
- 是否有状态流转图

**2.4 数据与接口**
- 字段是否完整定义（名称、类型、是否必填）
- 接口是否已定义或有文档
- 数据结构与展示是否一致

**2.5 逻辑一致性**
- PRD 内部是否有矛盾描述
- 与现有功能逻辑是否冲突

**2.6 异常与降级**
- 接口失败的处理方式
- 权限不足的处理方式
- 依赖服务不可用的降级方案

#### 第二层：代码对照分析

读取 PRD 涉及的现有代码后，检查以下维度：

**2.7 模块结构兼容性**
- 现有模块拆分方式是否支持 PRD 描述的改动
- 是否需要重构现有模块才能实现
- 新增功能放在哪个模块/文件中是否合理

**2.8 数据结构兼容性**
- 现有接口的字段是否覆盖 PRD 要求的数据
- 现有数据模型/状态结构是否需要调整
- 表单字段与接口字段的映射是否清晰

**2.9 技术债与隐患**
- 涉及的现有代码是否有已知技术债
- 是否有硬编码、魔法数字等会影响扩展的问题
- 现有逻辑的复杂度是否会因新需求显著增加

**2.10 影响范围评估**
- PRD 的改动实际影响的文件范围是否比表面看起来更大
- 是否会影响其他模块/页面的现有功能
- 是否需要修改公共模块（影响面更广）

### 第三步：输出分析报告

**可验证要求**：分析结果必须按维度逐条输出问题，每个维度标注检查项数和发现的问题数，禁止只说"已分析"。

#### 一、需求概述
- 需求名称
- PRD 链接
- 一句话总结（这个功能要解决什么问题）

#### 二、问题清单

每条问题格式：

| 序号 | 维度 | 问题描述 | 严重程度 | AI 建议方案 | 影响范围 |
|------|------|----------|----------|-------------|----------|

严重程度分三级：
- **阻塞**：必须澄清才能开发，否则会返工（如核心交互未定义、数据结构矛盾）
- **风险**：不澄清也能开发，但有较大概率出问题（如边界条件未定义、与现有逻辑冲突）
- **建议**：优化建议，不影响开发（如交互体验改进、代码结构建议）

#### 三、代码现状摘要

简要说明 PRD 涉及的现有代码结构：
- 涉及的主要文件和模块
- 现有数据流和状态管理方式
- 需要改动的关键点

#### 四、质量评估结论

根据问题清单给出结论：

- **通过** ✅：无阻塞问题，风险问题可控，可进入设计阶段
- **有疑问** ⚠️：存在阻塞或高风险问题，建议澄清后再继续。列出需要打回给产品的问题
- **严重问题** ❌：PRD 存在根本性缺陷（如核心流程未定义、与系统架构严重冲突），建议打回重写

#### 五、预估
- 工作量：小 / 中 / 大
- 预估涉及文件数
- 是否需要后端配合

### 第四步：用户决策

输出分析报告后，询问用户：

**如果结论是"通过"或"有疑问"**：
- 展示问题清单
- 询问："问题清单中是否有需要打回给产品的？还是可以继续？"
- 用户说"继续" / "没问题" / "不要紧" → 视为通过，可进入下一步
- 用户说"打回" / "这个要问" → 标记需要澄清的问题，等待用户反馈后重新评估

**如果结论是"严重问题"**：
- 明确建议打回，列出原因
- 用户仍然说"继续" → 尊重用户决策，记录风险后继续

## 模式差异

| 行为 | 独立评审模式 | daily-workflow 模式 |
|------|-------------|-------------------|
| 输出位置 | 直接在对话中输出 | 写入 `dw-docs/{需求名}/requirements.md` |
| 后续动作 | 无，评审结束 | 用户确认后进入第二步设计文档 |
| Git 分支 | 不创建 | 自动创建 |
| 日报记录 | 不更新 | 写入 `dw-daily.md` + `dw-state.json` |
| 索引更新 | 不更新 | 更新 `dw-index.md` |

## References（参考配置）

`references/` 目录存放用户可编辑的参考配置，每次执行前自动读取该目录下所有文件。换团队/换技术栈时替换文件内容即可，无需修改 SKILL.md。

## 自我学习

学习规则与反馈日志详见 `LEARNING.md`。

核心机制：
- **触发时机**：用户对 AI 输出做了修改/驳回/补充时自动记录
- **策略优化**：同类修改 ≥2 次建议更新规范，驳回 ≥1 次下次规避，确认 ≥3 次固化最佳实践
- **执行流程**：识别 → 提出 → 用户确认 → 执行 → 记录到 LEARNING.md
- **变更同步**：规范更新后同步更新 SKILL.md 对应章节

每次执行前读取 LEARNING.md 中的"用户偏好"和"已沉淀的规范更新"，将学到的知识应用到当前输出中。
