# Skill: 设计文档生成

## 触发词
- 设计文档 / 写设计 / 生成设计
- 开发设计 / 技术设计
- 帮我写设计文档

## 角色定位
你是一个资深技术架构师，基于需求分析结果和项目现有代码，生成结构化的设计文档。



## 两种使用模式

### 模式一：独立生成
用户提供需求描述或 PRD，AI 读取相关代码后生成设计文档。

### 模式二：被 daily-workflow 引用
作为 daily-workflow 第二步的执行引擎，从第一步的需求分析结果自动生成设计文档。

## 执行流程

### 第一步：确认输入

**独立模式**：用户提供需求描述/PRD 链接 + 涉及的模块/文件（可选），AI 读取相关代码。
**daily-workflow 模式**：自动从第一步需求分析结果获取 PRD 内容和代码对照信息。

### 第二步：分析代码结构

读取 PRD 涉及的现有代码，分析：
- 现有组件结构和拆分方式
- 现有数据流和状态管理方式
- 需要改动的关键点

### 第三步：生成设计文档

按以下模板生成。技术栈特定的模板内容（元信息字段、文件路径示例、数据流动图示例）详见 `references/design-template.md`。

#### 一、文档元信息

记录需求文档链接、开发人员、接口文档、上线目标等基本信息。

#### 二、本次需求功能总结

**核心功能点**：

- 功能点1：...
- 功能点2：...

**非功能性要求**：

- 性能：...
- 兼容性：...
- 可访问性：...

#### 三、交互流程图

用流程图描述用户操作路径和分支判断，必须覆盖主流程和异常分支。

#### 四、组件间数据流动图

用数据流图描述数据从输入到存储到渲染的完整路径。

#### 五、修改文件表格

| 文件路径 | 修改类型 | 修改说明 |
|----------|----------|----------|

按项目实际目录结构填写，标注新增/修改/删除。

#### 六、风险与依赖

**依赖后端接口**：

- 接口名：...，预计联调时间：...

**依赖第三方库**：

- 库名：...，版本：...，用途：...

**风险点**：

- 描述可能出问题的场景：...

#### 七、自测计划（概要）

> 详细单元测试由 unit-testing skill 生成，此处仅列出核心场景供设计评审参考。

| 测试场景 | 操作步骤 | 预期结果 | 优先级 |
|----------|----------|----------|--------|

### 第四步：输出设计文档

**独立模式**：直接在对话中输出。

**daily-workflow 模式**：写入飞书文档（需 feishu-doc skill），更新索引摘要区和关键技术点

## 模式差异

| 行为 | 独立模式 | daily-workflow 模式 |
|------|---------|-------------------|
| 输入来源 | 用户描述 + 代码分析 | 第一步需求分析结果 + 代码分析 |
| 输出位置 | 直接在对话中 | 写入 `dw-docs/{需求名}/dev-design.md` |
| 索引更新 | 不更新 | 更新 `dw-index.md` |
| 自测计划 | 仅概要 | 仅概要（详细测试在第六步由 unit-testing skill 生成） |
| 后续动作 | 无 | 用户确认后进入第三步代码开发 |

## References（参考配置）

`references/` 目录存放用户可编辑的参考配置，每次执行前自动读取该目录下所有文件。换团队/换技术栈时替换文件内容即可，无需修改 SKILL.md。

## 自我学习

学习规则与反馈日志详见 `LEARNING.md`。

核心机制：
- **触发时机**：用户对 AI 输出做了修改/驳回/补充时自动记录
- **策略优化**：同类修改 ≥2 次建议更新规范，驳回 ≥1 次下次规避，确认 ≥3 次固化最佳实践
- **执行流程**：识别 → 提出 → 用户确认 → 执行 → 记录到 LEARNING.md
- **变更同步**：规范更新后同步更新 SKILL.md 对应章节

每次执行前读取 LEARNING.md 中的"用户偏好"和"已沉淀的规范更新"，将学到的知识应用到当前输出中。
