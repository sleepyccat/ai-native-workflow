# 设计文档 Skill 学习机制

## 零、首次执行引导

> **AI 执行规则**：每次执行 skill 时检查下方日志表是否为空。如果为空（首次使用），在输出设计文档后主动告知用户：
>
> "💡 学习机制已启动：我会记录你对设计文档的反馈（结构调整/组件拆分/技术选型）用于持续优化设计策略。你可以随时查看 `LEARNING.md` 了解我学到了什么。"
>
> 此提示只在日志表为空时触发一次。

**记录执行检查清单**（AI 自检）：
- [ ] 用户调整了文档结构？→ 记录到日志表（修改）
- [ ] 用户否定了组件拆分方案？→ 记录到日志表（驳回）
- [ ] 用户补充了设计要求？→ 记录到日志表（补充）
- [ ] 用户修改了技术选型？→ 记录到日志表（修改）
- [ ] 用户直接接受了设计文档？→ 标记确认

## 一、反馈触发点

| 场景 | 记录什么 | 反馈类型 |
|------|---------|---------|
| 用户修改了交互流程图 | 哪个流程、AI 怎么画的、用户改成什么 | 修改 |
| 用户调整了组件拆分方式 | 哪个组件、AI 怎么拆的、用户怎么拆的 | 修改 |
| 用户补充了 AI 未识别的修改文件 | 文件路径、修改类型、修改说明 | 补充 |
| 用户删除了 AI 生成的某个章节 | 哪个章节、原因 | 驳回 |
| 用户调整了风险与依赖 | 哪个风险/依赖、用户看法 | 修改 |
| 用户直接接受了设计文档 | 哪个场景 | 确认 |
| 用户对数据流图有异议 | 哪段数据流、AI 怎么画的、用户纠正 | 修改 |
| 用户要求新增设计文档章节 | 章节名称、用途 | 补充 |

## 二、反馈记录

### 日志表

| 日期 | 场景 | AI 输出 | 用户反馈 | 反馈类型 | 调整动作 | 是否已沉淀 |
|------|------|---------|----------|----------|----------|------------|

反馈类型：
- `确认` — 用户直接接受
- `修改` — 用户接受但调整了
- `驳回` — 用户完全否定
- `补充` — 用户添加了 AI 未覆盖的内容

### 记录规则

- 只记录有实质反馈的交互
- 组件拆分方式的修改是高价值信号——说明 AI 对代码结构的理解有偏差
- 修改文件的遗漏也很重要——说明 AI 对影响范围的分析不够
- 用户删除章节可能意味着该章节不适用，需记录原因

## 三、策略优化

| 条件 | 动作 |
|------|------|
| 交互流程图被 `修改` ≥ 2 次 | 建议调整流程图的绘制策略或细节粒度 |
| 组件拆分方式被 `修改` ≥ 2 次 | 建议调整组件分析的策略 |
| 修改文件被 `补充` ≥ 2 次 | 建议增强影响范围分析的逻辑 |
| 某章节被 `驳回` ≥ 1 次 | 下次生成时默认跳过该章节，改为可选 |
| 某个设计模式连续被 `确认` ≥ 3 次 | 固化为默认设计方案 |

### 优化执行流程

1. **识别**：在设计文档生成过程中发现可优化点
2. **提出**：向用户描述问题和优化方案，说明影响 SKILL.md 的哪个部分
3. **确认**：等待用户确认，不自行修改
4. **执行**：用户确认后，更新 SKILL.md 对应模板或策略
5. **记录**：将变更记录到下方"已沉淀的规范更新"表中，并将日志表中对应记录标记为"已沉淀"
